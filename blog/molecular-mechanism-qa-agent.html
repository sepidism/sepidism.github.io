Building a Molecular Mechanism Q&A Agent

Sepideh Maleki · August 2025 · 12 min read

A scientist walks up to a system and asks: "What's known about the mechanism of action of rapamycin?" The system retrieves relevant literature, looks up the molecule in a database, synthesizes a grounded answer with citations, and flags any medical claims for human review before returning the result.

That's the agent I built. This post is about what I learned building it — the architecture decisions, the things that broke, and where the production patterns matter.

Why this project? I work on molecular perturbation prediction at Genentech. My day job is building ML models that predict how molecules behave when perturbed. But I kept noticing a gap: frontier models are incredible in papers, yet getting them to work reliably in production — with retrieval, tool use, observability, and safety checks — is a completely different skill. This project was my way of closing that gap.

The Architecture

The agent has four layers, each mapping to a production concern:

Scientist Question │ ▼ ┌──────────────────────────────────────┐ │ LangGraph StateGraph │ ← Orchestration │ │ │ [Retrieve] ──→ [Assess] │ │ ▲ │ │ │ │ ▼ │ │ │ [Tool Call] ───────────► │ ← MCP Server │ │ (lookup molecule via │ (wraps PubChem API) │ │ PubChem) │ │ │ │ │ │ └────←────[Synthesize] │ │ │ │ │ ▼ │ │ [Human Review] │ ← Human-in-the-loop │ │ │ │ ▼ │ │ Answer + Citations │ └──────────────────────────────────────┘ │ │ ▼ ▼ ┌──────────────────────────────────────┐ │ LangSmith Tracing + Evals │ ← Observability │ • Full trace per node │ │ • Faithfulness scoring (LLM-judge) │ │ • Cost & latency per step │ │ • Hallucination flags │ └──────────────────────────────────────┘ Corpus: Research papers (LaTeX → text) → Semantic chunking by section → bge-base-en-v1.5 embeddings → ChromaDB + BM25 hybrid retrieval → bge-reranker cross-encoder

I'll walk through each layer.

Layer 1: RAG — The Knowledge Base

The corpus is a set of research papers — my own NeurIPS submission on mechanism-aware mixture-of-experts plus a handful of related papers on molecular perturbation prediction. I control this corpus, which means I know what the right answers look like. That's important for evaluation.

Chunking: The Most Underestimated Variable

My first attempt was naive: fixed-size character splits at 1000 characters. The retrieval results were terrible. A chunk that ends mid-sentence gives the LLM an incomplete thought. A chunk that's too large drowns the relevant sentence in noise. I saw both failure modes immediately.

What actually worked: semantic chunking by section. Each chunk corresponds to one section of a paper — Introduction, Method, Experiments, etc. The key insight is that a section expresses one atomic concept. If someone asks "what method does this paper use?", the Method section is the right granularity — not a random 1000-character slice that might cut the method description in half.

I preserved metadata per chunk: paper title, section name, page number. This matters more than it seems — when the agent cites a source, the citation needs to trace back to a specific location, not just "some paper." In a pharma context, that traceability is non-negotiable.

Hybrid Retrieval

Semantic-only retrieval misses exact matches. If someone searches for "mTOR" or "rapamycin," keyword search finds those terms precisely where embedding similarity might rank them lower. BM25 (keyword) + dense vector search combined with Reciprocal Rank Fusion (RRF) gave noticeably better results than either approach alone.

The pipeline is: BM25 and vector search each return top-20 → RRF fuses the rankings → cross-encoder reranker (bge-reranker-base) re-scores the top candidates against the query → final top-5 chunks go to the LLM.

Lesson learned: Retrieval and reranking must use different models. First-stage retrieval (ANN search) is fast but imprecise. Reranking with a cross-encoder scores each query-document pair jointly, which is slower but dramatically more accurate. Don't try to make one model do both jobs.

Context Assembly

I initially concatenated the top-5 chunks by retrieval score. Then I learned about the "lost in the middle" problem: models attend more reliably to the start and end of the context window. Chunks buried in the middle get less attention. So I started front-loading the most relevant chunk — the one with the highest reranker score goes first, not the one that scored highest in raw retrieval.

Layer 2: LangGraph — The Orchestration

This is where the agent stops being a pipeline and starts being an agent.

I used LangGraph's StateGraph with five nodes: retrieve, assess, tool_call, synthesize, and human_review. The shared state is a typed dictionary that carries the question, retrieved chunks, tool results, draft answer, and review flags across nodes.

The critical design choice is the cycle: the agent retrieves, assesses whether it has enough information, and if it needs molecule details it calls a tool — then it may retrieve again. This loop is why I chose LangGraph over plain LangChain. LangChain's linear chains can't express "retrieve, evaluate, maybe loop back" naturally. LangGraph's graph model handles it as a first-class citizen.

Why not just LangChain?

LangChain's AgentExecutor is deprecated (maintenance mode until December 2026). The modern path is create_react_agent() for simple patterns or LangGraph's StateGraph for anything with loops, branching, or shared state. My agent has all three. The choice was clear.

Human-in-the-Loop

The human_review node is a LangGraph checkpoint. If the synthesize node produces an answer containing a medical claim (detected via a simple classifier), the graph pauses. A human reviews the answer and either approves or sends it back for revision. This is LangGraph's killer feature for regulated industries: pause the graph, wait for approval, resume deterministically. You can't bolt this onto a linear chain.

In a real Genentech deployment, this checkpoint is where a scientist reviews any agent output before it feeds into a downstream system. The audit trail shows exactly which nodes fired, what was retrieved, and who approved the final answer.

Layer 3: MCP — The Tool Interface

The agent needs to look up molecule information — molecular formula, weight, synonyms, known interactions. I built a Model Context Protocol (MCP) server that wraps the PubChem REST API. It exposes one tool:

Tool: lookup_molecule
Input: { name: "rapamycin" }
Output: {
    name: "Sirolimus",
    cid: 5284616,
    molecular_formula: "C51H79NO13",
    molecular_weight: 914.172,
    synonyms: ["Rapamycin", "Sirolimus", ...],
    description: "A macrolide..."
}

The server is ~50 lines of Python using the official mcp SDK, running over stdio (local transport — no auth needed for a demo). The agent calls it through LangChain's MCP adapter.

Why MCP instead of a custom function?

I could have written a plain Python function and passed it as a tool. But MCP gives you a standardized interface. Any agent — LangGraph, Claude, ChatGPT, Cursor — can call the same MCP server without custom integration. The tool description is registered once, and any model that speaks MCP can use it.

In production, this matters more. Instead of one PubChem tool, you'd have MCP servers wrapping internal compound databases, assay result APIs, clinical trial databases. Each one registered once, callable by any agent. The alternative — writing bespoke integrations for every model-tool pair — doesn't scale.

Security considerations

MCP has had real security issues: tool poisoning (malicious tool descriptions), prompt injection via tool outputs, and supply chain attacks through npm packages. For this demo with public data and local transport, the risk is minimal. But in production with proprietary data, I'd run MCP servers locally, enforce authentication on every server, and validate tool descriptions at registration time — not trust them implicitly at call time.

Layer 4: Observability — LangSmith + Evals

This is the layer that separates a demo from a production system.

The core problem: Traditional monitoring catches latency and errors. But the most dangerous failure mode in agentic systems is silent success — the agent follows flawed reasoning or hallucinates a tool call, and your metrics stay green. The output looks correct but came from broken reasoning. No latency chart will surface that.

Tracing

Setting LANGCHAIN_TRACING_V2=true with a LangSmith API key gives me automatic tracing of every node execution: inputs, outputs, tool calls, intermediate reasoning, token usage, and cost per step. The LangSmith dashboard shows the full execution graph — which nodes fired, in what order, and what each one produced.

This is invaluable for debugging. When the agent returned a wrong answer, I could replay the exact execution path and see: the retrieval node returned the wrong chunks because the BM25 query didn't match the paper's terminology. Without tracing, I'd be guessing.

Faithfulness Evaluation

After the synthesize node, I run an LLM-as-judge evaluation: "Is every claim in this answer supported by the retrieved context? Score 0.0 to 1.0." The score is logged to LangSmith alongside the trace.

If faithfulness drops below 0.7, the answer is routed to the human_review node instead of being returned directly. This catches the "the answer sounds confident but isn't grounded in the retrieved documents" failure mode — which is the most common one in my experience.

Building an Eval Dataset

I created 12 question-answer pairs from my paper domain — questions I knew the correct answers to. For each, I measure:

  • Retrieval precision@5: Did the retriever return the right chunks?
  • Faithfulness: Is the answer grounded in those chunks?
  • Answer correctness: Does the answer match the known correct answer?

This eval suite is how I know whether a change helps or hurts. Without it, I'm optimizing blindly. The rule I follow: change one variable at a time, run the eval suite, compare. Did switching from fixed-size to semantic chunking improve retrieval precision? The eval suite tells me — I don't have to eyeball it.

What I Learned

  1. Retrieval quality dominates generation quality. I spent more time on chunking, hybrid retrieval, and reranking than on prompt engineering. A better LLM can't fix garbage retrieval. This matches the research literature — a 2025 NAACL study found that tuning retrieval alone can improve task accuracy by over 50% with the same base model.
  2. Agents need loops, and loops need state. The retrieve → assess → tool call → retrieve cycle is fundamental to how agents work. LangGraph's StateGraph makes this natural; LangChain's linear chains make it awkward. If your agent needs to decide "do I have enough information?", you need a graph, not a chain.
  3. MCP is the right abstraction for tool interfaces. It decouples the tool from the agent framework. The same MCP server works with any model that speaks the protocol. In production, this means you can swap models without rewriting tool integrations.
  4. Observability is not optional for agents. Silent success is the enemy. Without tracing and faithfulness evals, you can't distinguish "the agent worked" from "the agent produced a confident wrong answer." In a pharma context, that distinction is everything.
  5. Human-in-the-loop is a feature, not a fallback. The checkpoint at human_review isn't there because the agent is bad. It's there because in a regulated context, some decisions should always have a human in the path. LangGraph's first-class support for this — pause, wait, resume — is what makes it production-ready for pharma.

What I'd Build Next

This is a prototype with public data. The architecture maps directly to a production system at Genentech:

  • The RAG corpus becomes internal protocols, SOPs, regulatory filings, and internal research reports — with access control so different teams see different documents.
  • The MCP server wraps internal compound databases, assay results, and clinical trial data instead of PubChem.
  • The human-in-the-loop checkpoint becomes mandatory for any output feeding into a regulated workflow.
  • The eval suite grows to hundreds of question-answer pairs, with automated regression testing on every model or prompt change.
  • Guardrails move from passive scoring (evals) to active blocking at the orchestration layer — intercepting PII leaks or ungrounded medical claims before they reach the user.

The stack — LangGraph + MCP + LangSmith + hybrid RAG — is the architecture I'd reach for. Not because it's trendy, but because each layer solves a real problem I encountered building this prototype.

This project was built to explore the production AI stack — RAG, agentic orchestration, MCP, and observability — applied to a domain I work in: molecular perturbation prediction. The code and architecture are mine; the opinions are based on what actually broke when I built it.
